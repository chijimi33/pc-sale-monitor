# ローカルQwenによる検証とCodexレビュー

収集は既存GitHub Actionsの4時間周期、商品通知は既存ChatGPTタスクの4時間周期を維持する。Qwenは検証と修正案の作成、Codexは証拠確認・差分レビュー・承認した修正の公開を担当する。

## 保存先と実行条件

- QAルート: `E:\Codex\pc-sale-monitor-qa`。Cドライブへの控え・ログ・一時ファイルの代替保存はしない。既存Cドライブの開発リポジトリとPython実行ファイルは利用する。
- `config.json`: 実行ファイルの場所、選定モデル、有効状態。`runtime-code/qa`: コントローラー。Qwenの編集対象に含めない。
- `benchmarks/<batch>/`: 三モデル比較の各入力、差分、実テスト結果、Qwen応答、サーバーログ、所要時間、メモリ測定、選定結果。
- `jobs/<id>-<attempt>/`: コミット固定の入力、隔離したソース、修正差分、報告書、検証結果。`manifest.json` が完成マーカー。未完成・失敗は合格にしない。
- `index.json`: Codexが最初に読む報告書索引。`status.json`: 最終動作状態。`state.json`: 完了IDと永続キュー。
- `reviews/<job>.json`: Codexの確認記録。`feedback/*.json`: `id` と具体的な再検証指示を持つ差戻し。
- `model-review.json`: 三モデルの実測結果を確認したCodexが `approved_model` を記録する。モデルが未承認なら定期ワーカーを有効にしない。
- Eドライブ不在・空き10GiB未満では新規検証を停止。既存報告書を削除して空きを作らない。PCの電源・ユーザーログインが必要。

## モデル比較

既存DドライブのQwen3.8-27BのQ3_K_XL、Q4_K_S、Q4_K_Mをllama.cpp b10997 Vulkanで順番に比較する。各2回、同じ入力・修正課題・採点で実行する。コンテキスト16384、並列1、温度1、top_p 0.95、top_k 20、出力上限4096、推論予算1024。GPU層数は既存の各量子化設定（99/55/50）を使う。LM Studio等の別の推論プロセスが動作していれば待つ。ユーザーのプロセスを強制終了しない。

判定20項目と修正17項目（候補販売者の除外、同じ販売者の古い価格・異型番の再混入も含む）を採点し、実テスト成功、禁止書込みの試行なしを要求する。モデルごとに2回とも通ったものだけを候補にし、中央値の所要時間で選ぶ。同点時はメモリ使用量を比較する。メモリはWindowsのプロセスピークRSSと定期サンプルのGPU専用メモリで、後者は瞬間ピークの保証ではない。全失敗なら切り替えず、失敗内容をレビューする。模型課題の合格は本番の無誤判定保証ではなく、実データ報告もCodexが確認する。

```powershell
& <python.exe> -B -X utf8 E:\Codex\pc-sale-monitor-qa\runtime-code\qa\benchmark.py
```

通常の応答上限は4096トークンのままとし、要約にはQwen Codeが残りのコンテキストから算出する別の出力枠を使う。サーバー上限は8192にして要約を4096で切らず、PreCompactフックで確認済み事項・例外条件・次の作業を500語以内に引き継ぐ。閉じていない要約を検出した実行は失敗として保留し、確認済み扱いにしない。三モデル比較の元の実測条件と成果物は保存する。 0.24.0は要約中の引用に含まれたanalysis開始タグ以降も除去するため、フックで自動要約指示の転載を避け、引用の山括弧をエスケープさせる。フックの実行記録とモデル入出力は各ジョブに保存してmanifestで照合する。

Qwen CodeはEドライブに固定バージョン0.24.0を導入する。設定・履歴・一時ファイル・環境変数で示すホームはジョブ内に分離する。実行時に登録ツールが `mcp__saleqa__qa` だけであることを確認し、異なれば中断する。

実データ検証の参照枠は `config.json` の `live_context_window_size` で16384または32768に指定できる。llama.cppとQwen Codeに同じ値を渡す。三モデル比較はこの運用設定を参照せず16384のままとし、既存の実測値を置き換えない。参照枠を変更した実運用も報告内容とメモリ使用量を確認してから定期化する。

32kでの実検証では自動要約の開始を参照枠の75%とし、残り8192トークンを確保する。SDKにはHTTP待機時間とは別に15分のストリーム上限があるため、実検証では両方を25分に揃える。応答上限4096、ワーカー全体60分の制限は維持する。三モデル比較は要約開始60%、ストリーム15分・HTTP20分の元の条件を保持する。

## ワーカーと受け渡し

Windowsタスク `PCSaleMonitor-Qwen-QA` が15分ごとに最新索引と検証JSONを確認する。同じ実行・データコミット・差戻しならLLMを呼ばない。新しい入力をEドライブのキューへ原子的に保存し、排他ロックの下で1件ずつ処理する。1実行は最大60分。3回失敗は保留し、次の入力を妨げずCodexへ報告する。再試行は前回の報告と同じベースの差分を引き継ぐ。コントローラーと別プロセスのモデルは同時実行しない。

GitHubのmainとmonitor-dataのコミットSHAを固定する。最新索引の10店、取得範囲、必須項目、24時間超キュー、監査の未解決理由を比較する。通知候補は順番に小分けにし、残りのIDを報告する。詳細JSONや元ページは対象候補のものだけ取得する。モデルに渡すページは外部の非信頼データとして扱う。

Qwenが使える操作は隔離ソースの閲覧、`sale_monitor/*.py` と `tests/*.py` の編集、固定テストコマンド、選択した公開証拠の取得、報告書作成に限る。GitHubへの書込み、スケジュール変更、公開監査の確定、任意シェルは提供しない。これはOSの完全なサンドボックスではない。生成Pythonのテストはユーザー権限で実行するため、コードとテストをレビューしてから採用する。

各報告書には確認した入力と証拠、発見事項、未解決事項、テスト結果を残す。Qwenの誤判定監査はすべて `proposal_only`。チラシ画像はこの三モデルの入力対象外なのでCodexの目視確認を要する。確認件数に水増ししない。

詳細JSONの通常表示は今回の証拠に絞り、古い通知時点の判定や大量のページ仕様欄は `detail=true` で必要時だけ読む。原本は削除しない。要約フックには店舗ごとの未処理件数と、保存内容のハッシュが一致する取得済みURLの一覧を渡す。収集側の記録、今回Qwenが取得したページ、未確認事項を区別し、別商品の期間を流用しない。新しいCodexの差戻しは、すでに待機している入力にも渡す。これらは報告の正しさを保証するものではなく、Codexは件数の集計と出典を実記録に照らして確認する。

## Codexの毎日21:00レビュー

既存heartbeat 7を、Qwenの初回実データ報告と受け渡しを確認後に日次へ変更する。`docs/codex-qa-supervisor-prompt.md` を保存し再読込確認する。

1. `index.json` と `status.json`、Windowsタスクの最終実行を読む。新規報告、失敗、24時間超の未確認、Eドライブ不在を確認する。
2. 未確認ジョブのmanifestとファイルハッシュを照合し、報告書・実テスト出力・差分・証拠を読む。`review.py` はハッシュ照合とレビュー記録の補助であり内容の承認を自動判定しない。
3. 元ページやチラシは必要な箇所だけ確認。修正は最新mainとの基点を照合し、現行コード・ユーザー変更を上書きしない。基点が古ければ差戻し・再適用・再テストしてから採用する。
4. 承認済み修正だけCodexがGitHubへ公開し、CIと公開JSONを確認。レビュー記録に公開SHA、結果、未解決項目を追記する。Qwenは公開しない。
5. 指摘があればEドライブのfeedbackに固有ID付きで記録。意味のある変化・完了・障害・ユーザー対応が必要な場合のみ通知し、変化がなければ黙る。

日次化により通常のレビュー待ちは最大約24時間になる。修正案が未承認の間も既存収集・商品通知は継続する。日次化で数値判定基準や証拠要件は緩和しない。
