# 設計仕様（経路・比較範囲・段階実行）

2026-11-11 に合意した再設計の仕様。実装・試験・文書はこの文書を正とする。

## 0. 変えないもの

- A/B の数値基準、同一性照合（`same_product`）、`Offer.errors()` の必須条件。
- 2026-11-12 に所有者の決定でBへ販売者履歴条件を追加した（criteria version 2）。数値閾値は変更しない。
- 不明を推測で埋めない。取得失敗・在庫切れ・正常な空結果を区別する。古い価格を現在比較に使わない。
- 履歴・観測・未反映 journal・イベント・配信状態・固定イベントIDを失わない。
- 楽天は除外。表示上の対象は10店のまま。有料サービスは使わない。
- ボット検知の回避（自動操作の隠蔽、指紋偽装、CAPTCHA 突破、プロキシの切替など）は実装しない。
  サイトが自動取得を拒否したら、その経路を止める。

## 1. 取得経路（route）

route は「販売者 × チャネル」を ID（例 `ark:direct`、`yahoo:api`、`amazon:chimolog`）とし、
機能ごとに状態を持つ。設定は `config/routes.json`、実行時の状態は `state/routes.json`。

機能: `sale_discovery`（セール一覧・セール商品）、`product_verify`（既知URLの商品確認）、
`comparison_lookup`（検索による比較先探索）、`shipping_policy`（送料規定の取得）。

状態:

| 状態 | 意味 | 疎通確認 |
| --- | --- | --- |
| `active` | 通常収集の対象 | — |
| `paused_maintenance` | サイト自体が停止中 | 1日1回・1リクエストで確認します。成功しても自動では戻さず、復旧候補として公開 JSON に出します。明示拒否なら `paused_refused` にします。 |
| `paused_refused` | 明示的に自動取得を拒否された | 行わない。人が設定を変えた時だけ復帰。手動 `probe` のみ |
| `paused_unreachable` | 無応答で原因未確定 | 週1回・1リクエストで確認します。成功しても自動では戻さず、復旧候補として公開 JSON に出します。明示拒否なら `paused_refused` にします。 |
| `paused_configuration` | 設定待ち（APIキー等） | 行わない |
| `not_implemented` | その機能の実装がない | — |

規則:

- `active` でない機能には、通常収集から一切通信しない。タスクも作らない。
- 疎通確認は通常収集と別に記録する。トップページの成功だけで他の機能を復旧扱いにしない。
  Retry-After を尊重する。
- 実行場所を変えても `paused_refused` は解除しない。
- `active` へ戻すのは、`config_revision` を上げる人の設定変更だけです。
  自動の遷移は、疎通確認で明示拒否を受けた `paused_maintenance`・`paused_unreachable` を `paused_refused` にするものだけです。
- 同じ `config_revision` の間だけ、`state/routes.json` の上記の自動遷移と疎通確認の記録を引き継ぎます。
  旧実装が保存した自動の `active` 遷移は採用しません。版が変わったら設定の値を使います。
- `successes_to_resume` は、復旧候補として表示するまでの連続成功回数です（初期値2回）。
  閾値に達した時に route の `recovery_candidate` に候補になった日時（`since`）、連続成功回数
  （`consecutive_successes`）、最終成功日時（`last_ok_at`）、直近の結果（`evidence`）を記録します。
  連続成功が途切れたら候補を消します。成功が続く間は `since` を保ちます。
- 公開 JSON に route ごとの状態・理由・開始日時・退避件数・`recovery_candidate`（候補がなければ `null`）を出します。

初期状態は `config/routes.json` を参照。

## 2. 実通信の予算

- ホストごとに最小間隔（`hosts.<host>.min_interval_seconds`、robots.txt の `Crawl-delay` があれば大きい方）と、
  段階の時間予算から導くリクエスト上限（`floor(秒数 / 間隔)`）を持つ。
- 一覧・商品・検索・送料規定・robots.txt・再試行・チラシ・ブラウザー遷移を、すべて同じカウンターに計上する。
- 中断・再開で予算は復活しない（run ID ごとに使用数を保存）。
- robots.txt は run ごと・ホストごとに1回取得する。Disallow に該当する URL は取得しない。
  robots.txt が 4xx（401/403 以外）なら制限なし、5xx・タイムアウト・401/403 ならその run ではそのホストを取得しない。
- 同一 run 内の同一リクエストへの重複需要は集約し、利用可能な成功応答を共有する。
  リクエストの同一性は URL だけでなく、HTTP メソッド・本文・取得方式（HTTP／ブラウザー）で判定する。
- 一時失敗の再試行や、明示拒否のないページに必要なブラウザー描画は、追加の実通信として予算に計上する。
- 明示的な拒否（403、アクセス確認画面）を受けたホストでは、その run でブラウザー描画へ進まない。

## 3. 実行構成

1つのジョブ・1つの CLI（`python -m sale_monitor.cli run`）が、次の段階を順に実行する。

| 段階 | 内容 | 通信 |
| --- | --- | --- |
| 0 準備 | 設定・状態スキーマ・scope 版の確認、期限の来た疎通確認 | 疎通確認のみ |
| A 発見 | `sale_discovery` が active の店で、セール一覧とセール商品を取得 | あり |
| B 計画 | 候補を選び、比較先確認の通信一式を予算から予約 | なし |
| C 確認 | 計画した比較先の商品ページ取得、上限付きの探索 | あり |
| D 判定 | A/B 判定、イベント、履歴反映、公開 JSON | なし |

- 構成は「調整役プロセス＋ホスト別の子プロセス」。A と C は店ごとに子プロセスを並行起動する。
- 各子プロセスと各段階に期限がある。期限切れの子は子孫（ブラウザー含む）ごと停止してから次へ進む
  （POSIX はプロセスグループ、Windows はプロセスツリーの停止）。
  期限切れの店の分は「未確認」とし、健全な店の結果で進める。
- run 全体の上限は `run.max_minutes`（初期値90分）。比較に使う観測は同一 run 内に限るので、
  観測間の時間差もこの上限に収まる。
- run ID で今回の観測と過去のチェックポイントを区別する。scope 版・設定版・状態スキーマ版が
  一致しない状態は使わない。
- 段階 D が失敗しても、収集済みの状態は保存する。GitHub Actions では異常終了後にも状態保存ステップを実行する。
- 実行場所は GitHub Actions と自宅PCのどちらでも動く。有効にするのは常に一方だけ（書き手は1つ）。

## 4. 比較の計画

比較依頼を「完了まで保持する債務」として持たない。毎 run、段階 B で計画し直す。
検索ページ送りの進捗・identity→URL の索引・確認結果は資産として保存する。

- **確認枠**: 候補ごとに「比較範囲内の既知比較先の確認一式」を予算から予約し、一式そろう候補だけ着手する。
  候補自身は段階 A の今回観測を使う。同じ成功応答を複数候補が使う場合は1回だけ数える。
- **探索枠**: 比較予算の `run.exploration_share`（初期値 0.2）を上限に、既知の比較先がない候補の検索を進める。
  未完なら「確認未完了」として残す。予算を超えない。未確認の比較先を落として成立させない。
  探索で見つけた商品 URL は、identity×店の `unverified_urls` に重複なく保存する。
  次回から確認一式に含め、1 URL を1リクエストとして確認枠から予約する。連続失敗の間隔延長も適用する。
  期限切れの子の保存済みキューからも未確認 URL を回収する。
  未確認 URL を取り除くのは、次のいずれかを今回の観測で確かめられた場合だけである。
  - 不一致の確定: ページの identity が候補と同じ種類（どちらも JAN、またはどちらもメーカー＋型番）で、値が異なる。
  - 既知比較先への移行: identity が一致し、今回のセール候補すべてと `same_product` が真で、
    必須条件を満たす観測（`Offer.errors()` が空）として保存された。以後は既知比較先の保留規則が引き継ぐ。
  取得できただけ、identity が取れない・種類が違う、構成が片方だけ不明、価格・送料等が不明、取得失敗、
  未到達の場合は取り除かず、保留を続ける。取り除いた URL は理由とともに `settled_urls` に残す。
  identity と `same_product` が一致する観測で在庫切れを検証できた場合は、その run の保留だけを解消する
  （`ended_urls` に run ID を記録）。URL は取り除かず、次回以降も確認一式に含め、次回未確認なら保留する。
  在庫が戻って必須条件を満たせば、既知比較先へ移行する。
  同じ商品 URL の確認を複数 identity で共有するときも、依頼元はソート済みの `plan_identities` で全件保持し、
  派生タスク・確認結果へ引き継ぐ。確認済み／未確認の記録と除外は `(identity, url)` 単位で行う。
  成功した商品タスクには `record()` した観測の `observed_offer_key` と `observed_url` を記録し、
  要求 URL が変わっていても、段階 D が渡す `offer_key` により今回 run の観測だけを結び付ける。
  同じ店・要求 URL に URL または確認結果のキーで結び付く観測は、最後の1件に絞らず全件を判定する。
  不一致確定には全観測の identity が同じ種類で対象と異なることを要求する。移行・在庫切れの run 限定解除には、
  対象 identity と一致する観測が1件以上あり、その全件がそれぞれの解除条件を満たすことを要求する。
  identity 不明・種類違いの観測が混在する場合や、一致する観測の条件がそろわない場合は保留を続ける。
- **優先度**: 履歴条件の成立、変化の種類（新着・値下げ・在庫復活）、保存済みの他店価格との差、
  最後に確認に成功してからの経過。履歴や古い他店価格は順位付けにだけ使い、対象からの除外には使わない。
- identity×店ごとに `last_attempt_at`、`last_success_at`、`consecutive_failures` を保存する
  （`state/comparison_tracking.json`）。連続失敗は間隔を指数的に空ける。
- 履歴評価は `engine.history_basis()` という純粋関数に切り出し、計画と `evaluate()` の両方が呼ぶ。
  計画に返すのは `met`／`not_met`／`insufficient` だけで、`accepted` は返さない。
  「3観測日以上・最古から30日以上・期間最低以下」は中央値による B の条件であり、
  年内観測最低の更新による B には追加しない。
  年内観測最低を500円以上更新する枝は、今年の有効履歴に対象販売者自身の観測が1件以上ある場合だけ `met`、
  なければ `insufficient`（`B_seller_history_missing_in_period`）とする。500円未満なら `not_met`、年内記録なしなら寄与しない。
  中央値の枝は、直近90日の全観測日で従来の条件を確認する。日数・期間不足は `insufficient`
  （`B_history_insufficient`）、価格条件の不成立は `not_met`（`B_history_gap_below_threshold`）。
  これが成立した場合だけ、対象販売者の有効観測がある日の、観測済み市場最低を日別に取り、その中央値より
  10%以上かつ500円以上安いことも確認する。対象販売者の観測日が3日以上・最古の自店観測から30日以上が必要で、
  自店観測なしは `B_seller_history_missing_in_period`、日数・期間不足は `B_seller_history_insufficient` として `insufficient`、
  自店観測日の中央値との差不足は `B_seller_history_gap_below_threshold` として `not_met` とする。
  同日の複数観測は1日とし、市場最低にはその日の全販売者を含める。金額は支払額・ポイント控除後額で別々に有効性を確認する。
  この変更は初観測の販売者だけでなく、既知の販売者に対する中央値Bも厳しくする。
  年内最安の枝の `met` を先に採用し、次に中央値の枝の `met` を採用する。どちらも成立しなければ、
  片方でも `insufficient` なら全体も `insufficient`、それ以外は `not_met`。理由は年内最安→中央値の順に重複排除し、成立時は空にする。
  `evaluate()` はAが成立せず、現在の独立比較先が2者以上あり、履歴の総合状態が `not_met` の場合だけ履歴理由で `rejected` にする。
  総合 `insufficient` を棄却しない。現在の安い比較先による棄却、Aの採用、Bに現在比較先1者以上が必要な条件は従来どおり。
  販売者条件を実際に評価した枝だけ `history.seller_history` に `seller_id` と `year`／`recent` を追加する。
  `year` は `status`（`present`／`missing`）、自店の `samples`・`from`・`to`、`recent` は `status`
  （`met`／`missing`／`insufficient`／`gap_below_threshold`）、自店の `samples`・`days`・`from`・`to` と、
  対象販売者の観測日における全販売者の `market_samples_on_seller_days`・`market_median_on_seller_days_yen` を残す。
  自店記録なしは件数0・日時null・市場中央値null。既存の市場全体の監査キーの意味・型・出力条件は保つ。
  年内最安が自店記録なしで続行した場合は中央値側の履歴（または空）へ `seller_history.year` を併記する。
  判定には `criteria_version: 2`、公開索引には scope の有無にかかわらず `decision_criteria_version: 2` を記録し、
  scope なしでも同じ新ルールを使う。発行済みイベントを書き換えず、基準変更だけで `ended` を作らない。
  今回 run の観測を過去履歴に混ぜない。
  過去 run の未反映 journal も履歴ファイルと合わせ、`observation_id` で重複排除して評価する。
  この統合は段階 B と scope ありの集計に適用する。scope なしの旧集計は出力互換のため従来の履歴入力を保つ。
- 発見側の古い探索課題は、関係する一覧を正常に読み終えてリンクがないと確認できた場合だけ、
  現在の探索対象から外す。確認できなければ「到達性不明」。どちらも販売終了を意味しない。

## 5. 比較範囲（scope）

`config/routes.json` の `scope` で版管理する。価格を見る前に固定し、run の途中で障害を理由に縮めない。
変更するときは `scope.version` を上げ、公開 JSON に記録する。

- 範囲内の既知比較先が今回未確認（一時失敗・予算不足・条件不明）なら、従来どおり保留する。
- 範囲は `scope.in_scope` に列挙した全店で固定し、`product_verify` の稼働状態には依存しない。
  確認可能な店は別に管理する。範囲内の確認不能な比較先が残る候補は `comparator_unverifiable` とし、
  他の比較先にも予約しない。公開する未確認経路には停止状態を理由として出す。
- 範囲内の他店に `unverified_urls` が残る間も保留する（`in_scope_comparator_url_not_verified`）。
  見つけた URL は次回の確認枠に含め、4章の規則で確かめられた場合だけ取り除く。
  範囲外や候補自身の店の未確認 URL は保留理由にしない。
- 範囲外の route にある既知比較先は、保留理由にしない。
- 同一 run で確認した有効な比較価格は、安いものも含めてすべて評価する。
- 判定結果と通知には「確認した販売者・チャネル」と「未確認の販売経路（範囲外／停止中／予算不足／
  取得失敗／条件不明）」を区別して必ず出す。判定名は範囲付き（例「A・比較範囲 v1」）。
  「10店で最安」とは表現しない。
- 比較で見つけた商品（`discovery_kind="comparison"`）も、今回のセール候補と同一の商品で全検証を通れば
  通知候補にする。発見経路は出典として残す。イベント ID は従来どおり `offer.key` から作る。
  昇格には `same_product` の一致を要求し、identity だけで中古・構成違い・保証条件違いを昇格させない。
  scope ありの過去イベント再評価にも同じ昇格条件を適用する。昇格できない比較商品の過去イベントは、
  今回の価格判定が accepted でも `currently_actionable=False`・`current_evidence=None` とする。

これは数値基準を変えずに、比較範囲を「10店」から「scope に列挙した販売者」へ変える仕様変更である。

## 6. 送料（後段）

- 送料規定ページは run ごと・店ごとに1回取得する。レビュー対象の「送料規定領域」のハッシュが
  レビュー済みの版と一致する場合だけ、構造化済みの規定を適用する。一致しない、または領域や例外条件を
  確実に抽出できない場合は、不明のまま保留してレビュー待ちに出す。
- 配送先は「配送プロファイル」（住所側の属性）として利用者が申告する。規定の例外条件がすべて
  プロファイルで判定できる場合だけ適用する。非公開の指定エリアなど、申告で解決できない例外が残る規定は
  適用しない。未設定なら不明のまま。
- 商品区分（大型・個別送料・単品購入不可）が一致する商品だけに適用する。

## 7. Yahoo（任意・後段）

Client ID があっても、次を満たすまで比較範囲に入れない: JAN 専用条件での検索と応答側の一致確認、
確認済みの販売者対応表、API で確定できる送料区分のみ採用、一般利用者に無条件で付くポイントのみ採用、
ページ送り上限の明示。Yahoo 店の価格はその販売者の Yahoo チャネルの価格として記録し、直販価格の確認とは扱わない。

## 8. 成功の定義と切替

- run の成功: 当該 run の正常な取得・解析結果があり、確認済みの空結果を区別でき、必要な成果物が整合している。
  正常なゼロ件は成功。古い観測の再保存だけ、疎通確認だけの実行は成功に数えない。
- 計測する指標: 公開成功の最大間隔、発見範囲の完了、選抜候補の一式確認達成率、範囲内 route の稼働率、
  通知時点の観測の鮮度。
- 正式切替（既存の通知タスクを JSON 方式へ切り替える）の必須条件:
  1. 新設計で7日間のベースラインを取り、サービス水準を決め、それを満たす。未決定の間は並行検証を続ける。
  2. 正式監査20件以上・誤通知0・未解決0。有効化している新機能を経た通知が監査に含まれる。
  3. 通知側が古い JSON・期限切れを「該当なし」と誤認しないことの実確認。
  4. 比較範囲と未確認経路が通知文に出ることの実確認。
- 「移行完了」と「正式切替」は別に記録する。

## 9. 移行

前提: 旧設計を前提に改修を続ける自動レビューを停止または更新する。

1. 旧方式の自動改修・状態更新を止め、実行中・待機中の書き手がないことを確認する。
2. 最終データ SHA を固定し、復元地点を確保する。
3. 冪等な移行を実行する（入力 SHA・移行版・元タスク ID・退避理由・元の作成日時を記録）。
   履歴・観測・未反映 journal・イベント・配信状態・固定イベント ID が変わらないことを確認する。
4. 新コードを、選んだ実行場所だけで有効化する。
5. 実行と公開を確認し、移行完了を記録する。撤回時に戻すコードと状態の組を明記する。

## 11. 試験の契約

- 停止中の経路への通常収集の通信がゼロである。
- 再開しても予算が復活しない。再試行・描画の追加通信はすべて予算を消費する。
- 同じ成功応答を複数候補が必要としても重複取得しない。同じ URL でも条件の違うリクエストは統合しない。
- 明示拒否の後にブラウザー描画へ進まない。
- 安い比較先の取得失敗を隠して候補を採用しない。取得失敗を旧価格で補わない。
- 範囲内の既知比較先が未確認なら保留し、範囲外は保留理由にしない。
- 販売者の重複を1者として数える。古い run の観測を現在比較に混ぜない。
- Bは対象の `seller_id` の有効な自店履歴を必要とし、他店だけの年内最安では成立させない。中央値Bでは、
  疎な自店の据置価格や自店の10%未満の変化を他店の日で水増しして成立させない。無効な送料・ポイント不明の履歴は対応する金額基準に数えない。
- 自店3観測日・最古から30日の境界、90日窓、JSTの年・日境界、同日重複、Fractionによる中央値を検証する。
  新Bが成立する固定入力では旧Bも成立する。全日条件が不成立なら自店条件を評価せず、評価した枝だけ監査情報を残す。
- 年内最安の自店履歴不足と中央値の差不足が併存しても総合 `insufficient` とし、比較先2者でも棄却しない。
  `insufficient` は採用済みイベント状態を保持し、再採用で重複 `qualified` を作らない。`rejected` 後の再採用は新しい `qualified` を作る。
- 今回 run の自店観測を履歴条件に使わず、scope あり・なしで基準版2を公開する。計画は自店条件不足の候補を除外せず、成立候補の後に並べる。
- 移行を2回実行しても結果が同じで、履歴・観測・イベントが変わらない。
- 実際の持越し状態のスナップショットから、段階 B〜D を通して公開 JSON まで生成できる。
- 共有 URL の確認結果は全依頼元へ渡り、別 identity の未確認記録を消さない。複数観測・URL 変更でも、
  今回の確定した証拠だけで未確認 URL を解除する。昇格できない比較商品の過去イベントを再通知しない。
- POSIX のグループ送信は、このパイプラインが `start_new_session=True` で起動し、独立グループを確認して
  所有印を付けた本物の `subprocess.Popen` だけに許可する。自身のグループには送らない。
  終了検知直後の回収は1回だけとし、期限切れでは最終グループシグナルを子の回収前に送る。
  所有印のない対象は個別の terminate／kill のみとし、偽プロセスへのグループ送信は Windows 上でも単体試験する。
