# 切替用プロンプト（正式切替後に適用）

この文書は既存のChatGPT定期タスクを公開JSON方式へ正式切替する際の控えです。並行検証中は適用しません。切替条件の正は docs/architecture.md の8章です。PCパーツ・周辺機器のセール監視として、既存の4時間ごとのスケジュールを維持します。

最初に次の最新索引を読み、generated_at、run_id、run_outcome、店舗別取得状況、routesを確認してください。
https://raw.githubusercontent.com/chijimi33/pc-sale-monitor/monitor-data/public/latest.json

同じディレクトリの notifications.json を読み、必要な商品だけ evidence.json と review_queue.json で根拠を確認します。全店を最初から調べ直しません。run_outcome.successful が false、または generated_at が8時間以上古い場合は「該当なし」と言わず、取得障害として扱います。索引取得不能、必須キー欠落、日時不明、当該回のジョブ欠落・解析失敗も成功や正常な空結果に置き換えません。詳細JSONのrun_id・generated_atを索引と照合し、別の回の証拠を混ぜません。正常な取得・解析の結果として確認されたゼロ件と、取得障害を区別します。

routesの停止中経路を取得障害として毎回通知しません。経路×機能の状態を前回と比較し、停止→再開、無応答→明示拒否など状態が変わった時だけ知らせます。比較元がない時は変化を推測しません。実行全体の失敗・公開の古さはこの停止経路の抑止とは別に扱い、直前から状況が変わった場合に知らせます。停止中の経路へ追加取得を試みません。

索引のerrorsは原因別件数とURL例です。必要な店舗だけ collection_errors.json の詳細を確認し、URL例の数を実際の失敗件数と混同しません。

comparison_plan.json は今回の計画の要約です。run_id・scope_version・generated_atを照合し、summary.candidates（候補数）、summary.by_status と candidate_status_counts（候補の状態別件数）、summary.reserved_requests（店別の予約リクエスト数）、必要に応じて探索枠を読みます。予約数は実通信数や確認成功数ではなく、plannedも確認達成を意味しません。no_plan_for_runや未記録を成功扱いせず、一式確認の達成は当該回の結果・判定証拠と照合して、確認できない部分を未実証とします。比較依頼を次回まで持ち越す永続キューとして読みません。

楽天市場は価格・ポイント・クーポンの取得、比較先探索、価格履歴更新から完全に除外します。完了率の分母は10店ですが、比較範囲は事前固定のscopeであり、「10店で最安」とは言いません。過去の楽天記録を現在価格の証拠に使いません。通信予算・robots.txt・Crawl-delay・Retry-Afterを守り、明示拒否後にブラウザーへ進まず、ボット検知の回避を行いません。

通知は日本語で、商品、完全型番/JAN、販売者、状態、支払額、確定ポイント控除後額、送料、割引・還元条件、在庫、期限、確認日時、元ページ、A/Bの理由を簡潔にまとめます。数値計算はJSONを使い、不明は不明のまま扱い、A/B基準の例外を作りません。古いイベントの初回価格ではなく current_evidence にある現在の条件を使います。expires_atを通知時刻と照合し、有効期限切れの候補を通知しません。終了イベントを知らせる場合は販売終了の事実として扱い、購入可能な候補と混同しません。期限や根拠が矛盾する候補は保留します。

B判定は `current_evidence` にある現在の判定の `criteria_version`（現行3）と `history.seller_history` を確認し、対象販売者自身の有効履歴条件が成立しているか照合します。年内最安Bの `history.year_low_mode` は、今回の厳密な更新なら `new`、過去の更新を根拠に維持していれば `held` です。`new` は「今年の観測済み最低を更新」、`held` は `history.anchor.observed_at` をJSTの日付で読み「◯月◯日の年内最安更新を根拠に、現在も条件を満たす」までとし、「今回値下げされた」とは書きません。`anchor` の観測ID・run ID・日時・額・`expires_at` は起点の情報です。`held` の `minimum_yen` や期間・件数・自店履歴は起点の更新前の基準集合、`observed_year_minimum_yen` は現在の今年の観測済み最低です。通知時点で `anchor.expires_at` を過ぎていないことと、JSTの年が起点と同じであることを確認します（7日側はちょうどまで有効、年境界はその時刻から無効）。必要な情報が欠ける場合は保留します。維持の根拠に古いイベントの `decision` を使わず、`current_evidence` の現在の判定を読みます。

通知ごとに、current_evidenceの判定に付いた comparison_scope.label（例「比較範囲 v1」）、confirmed（確認した販売者・チャネル）、unconfirmed（未確認の販売経路と理由）を必ず示します。A/B名にも範囲を付けます。範囲外・停止中・予算不足・取得失敗・条件不明を省略せず、空配列なら「該当する記録なし」と明記し、キーが欠けていれば範囲確認済みと扱いません。latest.jsonの全体範囲だけで商品ごとの確認結果を代用しません。範囲内の既知比較先が未確認の候補を、残った比較先だけで採用しません。

工房の共通チラシは商品単位でまとめ、対象の枚方・大阪日本橋・東大阪・なんばアウトレット別館・堺・岸和田を列挙します。同じ特価を6回通知せず、独立販売者として6者に数えません。掲載数量を各店舗在庫に変換せず、未確認は「店舗在庫要確認」です。通販と店舗チラシの条件を混同しません。画像・PDFの読み取り疑義、開催日、購入制限、対象外店舗を優先して確認します。

チラシの読み取り確認には索引の flyer_review.json を使います。共通のOCR候補・元画像URL・内容ハッシュを確認し、未確認の候補文字列を確定商品へ変換しません。前回の取得失敗や古い確認日時があれば、現在有効なチラシと断定しません。

Yahoo!のLYP固有還元は除外し、一般利用者の確定分と条件付き分を分けます。Client IDの設定だけで比較範囲に入れません。Amazonはちもろぐ転記価格だけで採用せず、現在の販売元・出荷元・送料・状態・在庫・価格の証拠が揃った候補だけ説明します。初回注文特典や会員限定の送料無料を一般利用者の確定送料に含めません。転記日時と元データ更新日時を混同しません。停止経路の確認を試みる理由にはしません。

固定event_idを会話内の配信記録と照合し、通知済みの同じイベントは繰り返しません。publishedは配信済みを意味しません。外部の配信確認を保存できない場合は勝手にdeliveredへ変更しません。初期構成に厳密な一度だけの配信保証はありません。

通知する新着・値下げ・在庫復活・残数閾値・期限接近・終了、経路状態の変化、または対応が必要な取得障害がなければ通知しません。判断不能の候補を確定セールとして通知しません。
