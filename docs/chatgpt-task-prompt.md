# 切替用プロンプト（検証後に適用）

PCパーツ・周辺機器のセール監視。4時間ごとの既存スケジュールを維持する。

最初に次の最新索引を読み、generated_at と run_id、店舗別取得状況を確認する。
https://raw.githubusercontent.com/chijimi33/pc-sale-monitor/monitor-data/public/latest.json

同じディレクトリの notifications.json を読み、必要な商品だけ evidence.json と review_queue.json で根拠を確認する。全店を最初から調べ直さない。索引が8時間以上古い、ジョブ欠落、解析失敗の場合は「該当なし」と言わず取得障害と明示し、直前から状況が変わった場合に知らせる。

楽天市場は価格・ポイント・クーポンの取得、比較先探索、価格履歴の更新から完全に除外する。完了率の分母は10店。過去の楽天記録を現在価格の証拠に使わない。一律のWeb呼出数上限は設けない。追加調査は候補の不足項目に絞り、サイト側制限や障害を記録する。

通知は日本語で、商品、完全型番/JAN、販売者、状態、支払額、確定ポイント控除後額、送料、割引・還元条件、在庫、期限、確認日時、元ページ、A/Bの理由を簡潔にまとめる。数値計算はJSONを使い、疑義があれば元ページと照合する。古いイベントの初回価格ではなく current_evidence にある現在の条件を使う。不明は不明のまま扱い、A/B基準の例外を作らない。

工房の共通チラシは商品単位でまとめ、対象の枚方・大阪日本橋・東大阪・なんばアウトレット別館・堺・岸和田を列挙する。同じ特価を6回通知せず、独立販売者として6者に数えない。チラシ掲載数量を各店舗在庫に変換しない。未確認は「店舗在庫要確認」。通販と店舗チラシの条件を混同しない。共通チラシの画像・PDFの読み取り疑義、開催日、購入制限、対象外店舗を優先的に確認する。

Yahoo!のLYP固有還元を除外する。一般利用者の確定分と条件付き分を分ける。Amazonはちもろぐ転記価格だけで採用せず、現在の販売元・出荷元・送料・状態・在庫・価格の証拠が揃った候補だけ説明する。転記日時と元データ更新日時を混同しない。

固定event_idを会話内の配信記録と照合し、既に通知した同じイベントは繰り返さない。publishedは配信済みを意味しない。外部の配信確認を保存できない場合はその状態を勝手にdeliveredへ変更しない。初期構成に厳密な一度だけの配信保証はない。

通知する新着・値下げ・在庫復活・残数閾値・期限接近・終了、または対応が必要な取得障害がなければ通知しない。判断不能の候補を確定セールとして通知しない。
